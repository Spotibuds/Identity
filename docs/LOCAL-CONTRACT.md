# Local Identity contract

The versioned application environment lives in `../Frontend/demo`. Start the full demo with its documented Compose commands. All dependencies and credentials are required configuration; there are no historical or cloud fallbacks. Identity listens on configured `ASPNETCORE_URLS`/`ASPNETCORE_HTTP_PORTS`, with Docker port 8080 and loopback host port 5101. PostgreSQL migrations and role creation retry at most ten times during startup. Mongo reconnects through one reusable driver client; `/health/live` is lightweight and `/health/ready` reports dependency or index failures as 503.

The container build pins SDK10.0.401, restores the committed dependency lockfile
in locked mode and publishes the net8 application into runtime8.0.31. Local test
execution therefore requires the .NET8 runtime even when using the .NET10 SDK.

Identity GUIDs identify actors, JWT subjects, owners, follows and listening events. Mongo ObjectIds identify profile documents, chats, messages and catalogue entities. Identity owns username, email, privacy and roles. User owns display name, biography, avatar, social state and history. `IdentityUserId` is uniquely indexed in the shared profile collection. Provisioning uses an upsert that preserves User-owned fields. User forwards account field updates through the restricted internal API. User and Music calls use the shared fresh service credential in `X-Spotibuds-Service`; this credential never belongs in the browser.

The durable PostgreSQL `ProfileSyncWork` outbox is committed with account changes. It retries bounded batches using exponential delay capped at one minute. Reconciliation and every authority mutation lock the same stable account row; an older in-flight remote write cannot overwrite a newer acknowledged synchronization. Registration with unavailable profile storage returns 503 with an explicit created-but-pending message. Login reconciles missing profiles idempotently before issuing a session. Role/privacy updates report pending synchronization on failure. Deletion first disables the account and revokes all sessions, then the outbox calls User's idempotent relationship/avatar/profile cleanup before deleting the Identity record. A pending deletion returns 202 and cannot authenticate. This single-instance demo does not claim a transaction across PostgreSQL, Mongo or Blob storage.

## Browser session

Use the frontend at `http://127.0.0.1:3100` and all APIs with the same host name. Credentials include is required on Identity login/refresh/logout/recovery. Do not mix `localhost` and `127.0.0.1`. Every cookie-writing request includes `X-Spotibuds-Request: 1`. A present Origin must be exactly allowlisted. Credentialed CORS has explicit origins, methods and headers. The custom header plus strict origin checks and SameSite Strict prevent cross-site cookie mutations; scripts can omit Origin but must supply the header. Cookies are HttpOnly and scoped to `/api/auth`; HTTP cookies are permitted only in explicit Development/Test environments. Other environments require HTTPS and Secure cookies.

- `POST /api/auth/register`: `{username,email,password,isPrivate?}`. Ordinary users receive only User role. Validation requires a 3–50 character username. Passwords require 8–100 characters, at least six unique characters, and uppercase, lowercase, digit and nonalphanumeric characters; the same policy applies to reset and change-password.
- `POST /api/auth/login`: `{username,password,rememberMe?}`. Returns `{token,user:{id,username,email,isPrivate,roles},expiresAt}` and the refresh cookie. No refresh credential is returned as JSON.
- `POST /api/auth/refresh`: empty body, cookie only; an expired or absent access token is allowed. Returns the same session shape.
- Browser renewal uses two phases with the same random UUID in `X-Spotibuds-Refresh-Request`. `POST /api/auth/refresh/prepare` returns 204, installs a pending HttpOnly cookie, and issues no access token; its predecessor remains unconsumed. After the response installs that cookie, `POST /api/auth/refresh/complete` consumes the predecessor and activates the installed successor atomically, returning the session shape without another Set-Cookie. The nonce is coordination state and grants no authentication.
- `POST /api/auth/logout` (alias `/revoke`): empty body; revokes the cookie's family and clears it; idempotent 204.
- `GET /api/auth/me`: valid access token and active session required; returns the user object.
- `POST /api/auth/change-password`: `{currentPassword,newPassword}`; revokes every account session and requires sign-in again.
- `POST /api/auth/forgot-password`: `{email}`; identical generic response for known/unknown addresses, with a real reset message to Mailpit for a known address. An unavailable mail sink returns 503 for both cases. Issuance locks the account and invalidates prior links in the same transaction, so concurrent requests leave one current link.
- `POST /api/auth/reset-password`: `{email,token,password}`; credentials expire after 20 minutes and are single-use. Successful reset revokes all sessions and every other outstanding recovery link under the same account lock. Invalid/expired/replayed credentials return 400.

Refresh and reset credentials are stored only as SHA-256 hashes. Access tokens expire after five minutes by default; refresh families expire after seven days without extending on rotation. Each activation or one-step rotation consumes one credential atomically in a PostgreSQL transaction while locking the stable session-family row. Concurrent one-step reuse produces at most one success; matching completion retries do not consume another credential. Any replay revokes the entire family, including the winning successor, so the user signs in again. The frontend must coordinate refreshes across tabs and must never restore a delayed session after logout. Logout and password/role changes invalidate access immediately through the session-family check; User and Music validate the signed `sid` claim through `GET /api/auth/internal/sessions/{sid}` (204 active, 401 revoked). Dependency failures fail closed with 503. User hubs must also check sid on each invocation and close when the access token expires.

The two-phase browser protocol removes the gap where navigation could discard a response cookie after the server consumed its predecessor. Within 30 seconds, the same nonce can recover an unconsumed preparation or reissue a lost completion body from the installed, still-unconsumed successor. Preparing that pending/just-completed successor with the same nonce does not create another successor. A different, missing or expired completion nonce cannot activate it. Reusing a consumed predecessor always revokes the family, including a matching nonce; there is no consumed-token grace exception. Pending credentials cannot use the legacy one-step refresh or authenticate an API. Preparation credentials are reproducible through a domain-separated keyed HMAC so PostgreSQL stores only hashes, including the nonce hash. Family locking limits preparation races; at most 16 recent pending stages are accepted per family, and expired pending rows are indexed and cleaned by the bounded worker. The nonce and stage state survive an API restart with the same injected signing key. The client keeps only the token-free nonce across interrupted navigation, bounds it to 30 seconds, and clears it on logout/account changes or terminal authentication failure.

## Administration and recovery

Role assignment, account updates/deletion and admin lists require Admin. Account details containing email/roles are limited to self or Admin. Role changes use an allowlist and revoke the target's sessions. Admins cannot demote/delete themselves. Lists return `{users,totalCount,page,pageSize}` with bounded pages. Search excludes unrelated private accounts and returns no email/roles. Email changes are explicitly unavailable because this demo does not implement external email verification; current email display and password recovery remain functional.

Internal profile routes use typed camelCase contracts and service authorization: `GET internal/users/{guid}`, `GET internal/users?page=1&pageSize=100`, `POST internal/profile {identityUserId,userName?,isPrivate?}`. The service list is an envelope, not an array. Public connection-string diagnostics and token parsing diagnostics are absent. Errors and logs never include credentials, connection-string prefixes or recovery tokens.

Local administrator creation is enabled only with `LocalDemo:Enabled=true` in Development and explicit username/email/password. If an ordinary preexisting account conflicts, startup refuses to promote it. Ordinary demo accounts are created by the seed script. Public account endpoints have a bounded per-IP limiter (100 requests/minute), and password lockout is five failed attempts for 15 minutes. External mail verification, distributed replicas and production secret revocation are separate production follow-ups.

## Verification

Run `dotnet build Identity.sln` and `dotnet test tests/Identity.Tests/Identity.Tests.csproj` from Identity. The committed tests exercise real authorization/JWT middleware and a persisted disposable SQLite database, including negative side-effect assertions and account/session/outbox state. They use controlled SMTP/profile adapters; full-stack Mailpit/Mongo/PostgreSQL checks are separate and recorded in the shared demo verification ledger. Run `dotnet list Identity.csproj package --vulnerable --include-transitive` for current NuGet advisory data. CI builds/tests and builds a local Docker image without publishing or deployment secrets.
